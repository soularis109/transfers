# Обмеження проєкту

Це тестове завдання на позицію Frontend Developer. Оцінюють: відповідність ТЗ,
якість верстки, чистоту архітектури, тести. Код має бути охайним, але **не
переускладненим** — абстракція без потреби тут мінус, а не плюс.

## Чіпати заборонено

Ці речі вже узгоджені, звірені й зафіксовані. Не змінювати без явного дозволу:

1. **`src/app/styles/abstracts/_variables.scss`** — токени зняті попіксельно
   з макета Figma. Нових кольорів/розмірів не вигадувати, наявні не правити.
2. **HTML-структура і BEM-класи в `ui/`-компонентах** — верстка фінально
   звірена з макетом. Рефакторинг стосується TypeScript, Redux і структури
   файлів, а не розмітки.
3. **`carrier`-логотип у `TicketCard`** — статична картинка `a4e.webp`
   відповідає дизайну. Рішення «залишаємо як є» вже прийняте, не пропонувати
   заміну на текстовий код чи інші варіанти.

`public/data/tickets.json` — дані довільні (ТЗ лише каже "як базу даних можна
взяти звичайний JSON-файл", вимоги на незмінність даних нема), тому їх можна
доповнювати за потреби, наприклад щоб наочно продемонструвати тай-брейк
сортування. Але не ламай мовчки вже наявні нічиї по тривалості (кілька пар
квитків з однаковим сумарним часом польоту й різною кількістю пересадок) —
вони показують, що "Оптимальний" і "Найшвидший" справді можуть давати різний
порядок.

Якщо зміна в дозволеній зоні неминуче зачіпає щось із цього списку — **зупинись
і спитай**, не роби мовчки.

## Вимоги ТЗ, які не можна порушити

- React + Redux + TypeScript.
- **CSS-фреймворки заборонені.** Ніякого Bootstrap / Tailwind / MUI, ні в
  залежностях, ні utility-класами вручну.
- Стилі — тільки Sass. `@import` заборонений як deprecated, лише `@use` / `@forward`.
- **BEM обов'язковий** у всіх `.scss`: `block__element--modifier`.
- `stylelint` з конфігом `stylelint-config-standard-scss`. Кастомний
  `selector-class-pattern` під BEM — це необхідний фікс, а не «вимкнене правило»:
  дефолтний kebab-case патерн конфліктує з `__` і `--`. Інші правила вимикати
  заради обходу проблеми не можна — проблему треба вирішувати.
- Hover-стан на **кожному** інтерактивному елементі: логотип, рядки фільтра,
  чекбокси, таби, картки, кнопка.
- Деплой на GitHub Pages, `base: '/transfers/'` у `vite.config.ts`.
  Шляхи до статики — через `import.meta.env.BASE_URL`, ніколи хардкод `/`.

## Робочий процес

**Один логічний крок = один коміт.** Ніяких великих комітів «в кінці на все».
Формат: `type(scope): опис` — `refactor(entities/ticket): ...`,
`fix(features/stops-filter): ...`, `test(shared/lib): ...`.

**Після кожного коміту** — повна верифікація:

```bash
npm run lint
npm run lint:styles
npm test
npm run build
```

Якщо щось червоне — виправ або відкоти **перед** наступним кроком. Борг не накопичувати.

**Кількість тестів після змін не може бути меншою**, ніж до них. Якщо тест
видалено — пояснити чому.

## Звітність

Не рапортувати «готово» без реального виводу команд. У звіті обов'язково:

- `git status` (має бути чисто)
- `git log --oneline` (список нових комітів)
- реальний вивід `npm test` з кількістю тестів
- підтвердження успішного `npm run build`

Якщо щось із запланованого не зроблено — сказати прямо, які пункти і чому.
Часткове виконання, назване повним, гірше за чесне «не встиг».

## Чесність аналізу

Якщо гіпотеза про проблему не підтвердилась — так і сказати, не підтасовувати
знахідку під очікування. Порожній результат перевірки — валідний результат.

Не вигадувати роботу заради обсягу звіту. Якщо в якомусь напрямку проблем немає —
одне речення «перевірено, чисто» замість розлогого тексту.
